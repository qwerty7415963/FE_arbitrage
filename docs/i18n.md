# i18n Guide

## Overview

The frontend uses `next-intl` with two locales: `vi` (default) and `en`. Messages live in `src/messages/en.json` and `src/messages/vi.json`.

## Adding new translations

1. Add the key to both `en.json` and `vi.json` with identical structure.
2. Use `useTranslations('namespace')` in client components and `getTranslations` in server components.
3. Keep keys namespaced by feature (e.g. `traders.overview.title`).
4. Run the parity test: `pnpm test tests/unit/lib/messages-parity.test.ts`.

## Namespace conventions

- `common`: shared labels, actions, pagination, language switcher.
- `navigation`: sidebar/top nav labels.
- `traders`: trader scanner, detail, overview, buckets.
- `wallet`: wallet detail tabs and fields.
- `groups`: group management.
- `settings`: settings page.
- `notifications`: Telegram notifications.
- `errors`: error code mapping targets.
- `fundingArbitrage`: funding arbitrage table and filters.

## Error code mapping

Backend error codes are mapped to message keys via `src/lib/error-mapping.ts` (`mapErrorCode`).

- Known backend codes (e.g. `AUTH-004`, `GROUP-002`, `COMMON-902`) map to `errors.<CODE>`.
- Special transport codes map to friendly keys: `NETWORK_ERROR -> errors.network`, `TIMEOUT -> errors.timeout`, `ABORTED -> errors.aborted`.
- Unknown or missing codes map to `errors.unknown`.

When adding a new backend error code, add it to the `errors` namespace in both message files; `mapErrorCode` resolves it automatically because known codes are derived from `en.json`.

## Locale-aware formatting

`src/lib/trader-format.ts` accepts an optional locale on `formatRelativeTime` and `formatDateTimeUtc`. Output stays stable (UTC / English abbreviations) by design; components localize surrounding text via messages.
